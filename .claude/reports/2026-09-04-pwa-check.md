## 발견 목록

### [높음] F-1. install의 `cache.addAll`에 리다이렉트되는 `/index.html`이 포함되어 서비스워커 install 전체가 실패한다

- **위치**: `sw.js:6-10`(APP_SHELL), `sw.js:20`(`cache.addAll([...APP_SHELL, ...STATIC_ASSETS])`)
- **스펙 근거**:
  - W3C Service Workers / MDN `Cache.add()`·`Cache.addAll()`: 내부적으로 `fetch` 후 `Cache.put()`을 호출하는데, 응답이 리다이렉트를 거친 경우(`response.redirected === true`) Chromium의 `Cache.put()`은 `TypeError`("Cache.put() encountered a redirected response ... not supported")를 던진다. `addAll`은 항목 중 하나라도 실패하면 반환 프라미스 전체가 reject된다.
  - `install` 핸들러의 `event.waitUntil(...)`에 넘긴 프라미스가 reject되면 해당 서비스워커는 install 실패로 폐기되어 **활성화되지 않는다**.
  - sw.js 주석(37-38행)이 스스로 명시: "`'/index.html'` 등은 Cloudflare Pages가 308로 `'/'`에 리다이렉트한다." 즉 배포 환경에서 `/index.html` 요청은 항상 redirected 응답이 된다.
- **실패 시나리오**:
  1. 새 코드와 함께 `CACHE_NAME`을 v49로 올려 배포한다.
  2. 브라우저가 새 `sw.js`를 받아 install 하며 `cache.addAll(['/', '/index.html', '/manifest.webmanifest', ...])`를 실행한다.
  3. `/index.html`이 308로 `/`에 리다이렉트 → 그 응답으로 `cache.put` 시도 → `TypeError` → `addAll` reject → install 실패.
  4. 기존 v48 서비스워커가 계속 유지되고 새 버전은 활성화되지 않는다. 배포해도 SW 레벨 프리캐시가 갱신되지 않고, 신규 방문자는 프리캐시가 하나도 없어 오프라인이 완전히 깨진다.
  - 런타임 `networkFirst`에는 `cleanRedirect`(39-46행) 우회가 있으나 `install` 경로에는 적용되지 않는 비대칭 구조.
- **수정 제안**:
  - APP_SHELL에서 `/index.html`을 제거하고 `/`만 프리캐시한다(내비게이션 폴백도 `cache.match('/')`를 쓰므로 `/`만으로 충분).
  - 또는 install에서 개별 `fetch` 후 `response.redirected`면 `cleanRedirect`를 거쳐 `cache.put` 하도록 직접 구현하고, 각 자산을 `Promise.allSettled`로 처리해 일부 실패가 install 전체를 무너뜨리지 않게 한다.
    ```js
    self.addEventListener('install', (event) => {
      event.waitUntil((async () => {
        const cache = await caches.open(CACHE_NAME);
        await Promise.allSettled(
          [...APP_SHELL, ...STATIC_ASSETS].map(async (path) => {
            const res = await fetch(path, { cache: 'reload' });
            if (!res || !res.ok) return;
            await cache.put(path, res.redirected ? await cleanRedirect(res) : res);
          })
        );
        await self.skipWaiting();
      })());
    });
    ```

### [높음] F-2. manifest가 선언한 아이콘 크기와 실제 파일 픽셀이 불일치한다 (192 항목)

- **위치**: `manifest.webmanifest:11-16` (`"src": "/icons/icon-192.png"`, `"sizes": "192x192"`), 실제 파일 `/home/gon/calc-note/icons/icon-192.png`
- **측정값(이번 점검 재확인)**: `identify` 결과 `icon-192.png` = 실제 **500x500** PNG(8-bit sRGB). `icon-512.png` = 512x512(일치).
- **스펙 근거**: W3C Web App Manifest — `icons[].sizes`는 리소스의 실제 크기와 일치해야 한다. Chromium은 매니페스트 파싱 시 선언 크기와 비트맵 실제 크기를 대조해 불일치 시 "Actual size (500x500) of icon ... does not match specified size (192x192)" 경고를 남기고 해당 항목을 설치 가능성(installability) 판정에서 제외할 수 있다. 설치 프롬프트는 192px 이상 + 512px 이상 아이콘을 요구하므로, 192 항목이 무효 처리되면 프롬프트 조건이 흔들린다.
- **실패 시나리오**: 안드로이드 Chrome에서 "홈 화면에 추가" 프롬프트가 뜨지 않거나, 홈 아이콘/스플래시가 512 항목만으로 스케일되어 저해상도 기기에서 과도하게 다운스케일된 아이콘이 표시된다. Lighthouse PWA 감사에서 아이콘 경고 발생.
- **수정 제안**: `icon-192.png`를 정확히 192x192로 다시 렌더링해 교체(권장). 파일을 그대로 둘 경우에만 매니페스트 항목 `sizes`를 `"500x500"`으로 정정. 384/256 등 중간 크기 추가는 선택.

### [중간] F-3. `theme_color` 값이 manifest와 `<meta name="theme-color">`에서 서로 다르다

- **위치**: `manifest.webmanifest:8` → `#5B54E8`, `index.html:6` → `<meta name="theme-color" content="#F5F6FB">`
- **스펙 근거**: 두 값 모두 유효하지만 역할이 겹친다. 설치된 PWA(standalone)의 상단 시스템 바 색은 manifest `theme_color`를, 일반 브라우저 탭/주소창 테두리 색은 `<meta>` 값을 사용한다. 값이 다르면 "브라우저에서 열었을 때"와 "설치 후 실행했을 때" 상단 색이 급변한다. 앱의 실제 배경 토큰은 `--bg:#F5F6FB`(index.html:16)이고 `#5B54E8`는 액센트(`--accent`) 색이다.
- **실패 시나리오**: 설치한 앱을 열면 헤더는 흰/연회색인데 시스템 상태바만 보라색(#5B54E8)으로 떠 이질감이 생기고, 브라우저에서는 연회색이라 일관성이 없다.
- **수정 제안**: 의도한 상태바 색 하나로 통일. 앱 셸이 밝은 배경이므로 manifest `theme_color`도 `#F5F6FB`(또는 헤더와 같은 색)로 맞추는 것을 권장. 보라색 상태바가 의도라면 `<meta>`를 `#5B54E8`로 변경.

### [중간] F-4. 아이콘 2개 모두 `"purpose": "any maskable"` 단일 선언 — 세이프존 미확보 시 로고가 잘린다

- **위치**: `manifest.webmanifest:15`, `manifest.webmanifest:21`
- **스펙 근거**: W3C Manifest `purpose` — `"any maskable"`은 같은 비트맵을 (a) 여백 없이 그대로, (b) 마스크(원/스쿼클)로 잘라내는 두 용도에 모두 쓰겠다는 선언이다. maskable 스펙은 아이콘의 최소 안전 영역을 중앙 지름 80% 원("safe zone")으로 규정하며, 핵심 콘텐츠는 그 안(권장 40% 반경)에 있어야 한다. 원본이 가장자리까지 로고/배경을 채우면 마스킹 시 모서리와 로고 일부가 잘리고, 반대로 여백을 넉넉히 준 아이콘을 `any`로 쓰면 로고가 작게 보인다.
- **실패 시나리오**: 안드로이드(마스커블 아이콘을 실제로 원형/스쿼클로 자름)에서 홈 화면 아이콘의 테두리 그래픽이 잘리거나 로고가 원 안에서 지나치게 작게 렌더된다. https://maskable.app 에서 육안 확인 가능.
- **수정 제안**:
  - `any` 전용 항목과 `maskable` 전용 항목을 분리 선언한다.
  - `maskable` 전용 아이콘은 별도 파일로, 사방 ~10% 이상(권장 20%) 패딩과 꽉 찬 배경색을 넣어 제작한다.
    ```json
    "icons": [
      { "src": "/icons/icon-192.png", "sizes": "192x192", "type": "image/png", "purpose": "any" },
      { "src": "/icons/icon-512.png", "sizes": "512x512", "type": "image/png", "purpose": "any" },
      { "src": "/icons/icon-192-maskable.png", "sizes": "192x192", "type": "image/png", "purpose": "maskable" },
      { "src": "/icons/icon-512-maskable.png", "sizes": "512x512", "type": "image/png", "purpose": "maskable" }
    ]
    ```
  - 새 maskable 파일을 추가하면 `sw.js`의 `STATIC_ASSETS`에도 넣어 오프라인 설치 화면에서 깨지지 않게 한다.

### [중간] F-5. 외부 CDN Tabler 아이콘 웹폰트가 프리캐시/런타임 캐시 대상이 아니라 오프라인에서 깨진다

- **위치**: `index.html:12` (`<link rel="stylesheet" href="https://cdn.jsdelivr.net/npm/@tabler/icons-webfont@3.19.0/dist/tabler-icons.min.css">`), 사용처 예: 백스페이스 `ti ti-backspace-filled`, 스왑 화살표 `ti ti-arrows-up-down`(index.html:432), 옥외광고 `ti ti-plus`/`ti ti-file-spreadsheet`
- **스펙 근거**: `sw.js:93`에서 `url.origin !== self.location.origin`인 요청은 `respondWith` 없이 그대로 통과시킨다(cross-origin 미개입은 환율 API 때문에 올바른 정책). 그 결과 `cdn.jsdelivr.net`의 CSS와 뒤이어 로드되는 woff2 폰트는 SW 캐시에 전혀 담기지 않고 `install`의 `addAll` 목록에도 없다. 오프라인 부팅 시 아이콘 글리프가 로드되지 않는다.
- **실패 시나리오**: 온라인에서 한 번 연 뒤 비행기모드 재실행 → HTML/JS는 network-first 캐시 폴백으로 뜨지만, 백스페이스·스왑·옥외광고 추가/다운로드 버튼의 아이콘이 빈 네모(tofu)로 표시돼 기능 인지가 어렵다. (환율 API 무응답은 `loadFX` try/catch로 "환율 로드 실패 (오프라인 모드)" 문구 처리되어 있어 그 부분은 양호.)
- **수정 제안**:
  - 필요한 소수 글리프만 로컬 SVG/인라인으로 대체해 외부 폰트 의존 제거(가장 견고).
  - 유지한다면 Tabler CSS/woff2를 빌드 시 `/vendor/` 아래로 복사해 same-origin으로 서빙하고 `sw.js`의 `STATIC_ASSETS`(cache-first 분기)에 추가.
  - 차선책: fetch 핸들러에 `cdn.jsdelivr.net` 호스트 한정 cache-first 예외를 두되 opaque 응답 캐싱의 한계(용량·무결성)를 감수.

## 참고(낮음 — 요약에는 포함하지 않음)

- **L-1. `id` 필드 없음** (`manifest.webmanifest`): 필수는 아니나 권장. 없으면 `start_url`(`/`)에서 앱 식별자가 파생되어, 향후 `start_url` 변경 시 다른 앱으로 인식돼 설치가 중복될 수 있다. `"id": "/"` 명시 권장.
- **L-2. `scope` 미지정**: 생략 시 `start_url` 기준 디렉터리(`/`)가 스코프가 되어 단일 페이지 앱에서는 문제 없음. `"scope": "/"` 명시로 의도를 분명히.
- **L-3. `short_name` == `name`** (`manifest.webmanifest:2-3`): 둘 다 "계산 노트". 동작상 문제 없음(4자라 무방).
- **L-4. `networkFirst`가 non-OK 응답에서 캐시 폴백하지 않음** (`sw.js:72`): `fetch`는 성공했으나 서버가 4xx/5xx면 `return response;`로 그대로 반환하고 캐시를 시도하지 않는다. 서버 장애 시 캐시된 정상 셸이 있어도 오류 페이지가 노출될 수 있다. `!response.ok`면 `cache.match` 폴백 시도 권장.
- **L-5. `apple-touch-icon`이 500x500 파일을 가리킴** (`index.html:11` → `/icons/icon-192.png`): iOS 권장은 180x180. 동작은 하나 다운스케일되므로 전용 180px 파일 추가가 이상적.
- **L-6. `orientation: "portrait"`** (`manifest.webmanifest:9`): 계산기 앱 특성상 타당. 이슈 아님(기록용).

## 양호 확인 항목

- `<link rel="manifest" href="/manifest.webmanifest">`(index.html:10) 경로/파일명 일치.
- 필수 manifest 필드(`name`, `short_name`, `start_url`, `display`, `icons`, `theme_color`, `background_color`) 모두 존재·형식 유효.
- `display: "standalone"` — 단일 화면 유틸리티 앱에 적정.
- SW 등록 코드(index.html:1647-1651): `load` 이벤트 뒤 `/sw.js` 등록, `.catch(console.error)`로 예외 처리. 정상.
- 내비게이션/앱 셸 요청이 `networkFirst`로 처리됨(sw.js:97-98) — 프로젝트 규칙(network-first) 부합.
- 이미지 요청만 `cacheFirst` 분기(sw.js:48-50, 95-96) — 의도대로.
- cross-origin(환율 API `open.er-api.com`, index.html:1014) 요청은 SW가 통과시킴(sw.js:90-93) — 올바름.
- `install`에서 `skipWaiting()`, `activate`에서 `clients.claim()` + 옛 캐시 삭제(sw.js:23, 26-35) 존재.
- `cleanRedirect`(sw.js:39-46): 런타임 network-first 경로에서 redirected 응답을 정제해 `respondWith`에 넘김 — 정확. (단, install 경로에는 미적용: F-1 참조.)
- 내비게이션 오프라인 폴백이 `cache.match('/')` 사용(sw.js:79-82)하고 `/`는 프리캐시 목록에 포함 — 단 F-1로 install이 실패하면 무력화됨.
- 환율 API 오프라인 시 UX: `loadFX` try/catch로 상태 문구 갱신(index.html:1022-1023) — 양호.
